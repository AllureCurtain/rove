## 3. 候选专利点

### 候选点一：文件工件与 SQLite 索引协同的智能体任务可恢复状态管理

- 技术背景：智能体任务通常包含模型流式输出、工具调用、审批、输入等待、计划步骤、记忆加载和最终报告等多类事件。若仅依赖进程内状态，服务重启后难以查询历史和恢复；若仅依赖数据库，则调试和迁移不便。
- 创新点：将 `.rove/runs/<run_id>/trace.jsonl`、`task_state.json`、`report.json` 作为可读事实工件，同时用 SQLite 保存 session/job/run/event/report/task-state 元数据、pending approval/input 和 replay offset；维修时从文件工件重建索引，并跳过损坏 trace 行。
- 与现有技术区别：不是单纯工作流数据库持久化，也不是普通日志落盘，而是以文件为事实资产、SQLite 为可重建索引，并与智能体事件流、恢复快照和 API SSE replay 结合。
- 可实施性：项目已有 `StateStore`、`StateIndex`、`RunArtifactRecorder`、`TraceWriter`、`state repair/cleanup` 等实现。

### 候选点二：提示检查点、分层记忆与确定性/模型生成压缩的长任务恢复

- 技术背景：长会话智能体运行中，直接回放全量历史容易超出模型上下文窗口；简单截断会丢失计划进度、工具结果和记忆引用。
- 创新点：以固定提示顺序构造上下文：system、durable memory、session memory、compact summary、recent history tail、current user message；在 `PromptCheckpoint` 中保存 summary、preserved tail、plan、memory pointer、last step、last event seq、token estimate、compacted count 和 compaction 状态；当触发压缩时优先使用模型生成摘要，失败后写入确定性摘要并在连续失败后打开降级熔断。
- 与现有技术区别：不是一般的提示压缩算法，而是把压缩结果作为可恢复运行时检查点，与运行事件序号、计划进度和记忆路径绑定。
- 可实施性：项目已有 `ContextManager`、`PromptCheckpoint`、`CompactionRuntime`、`RunArtifactRecorder` 等实现。

### 候选点三：基于工具安全标注、审批策略与确定性回写的批次工具编排

- 技术背景：智能体模型可能在一次响应中提出多个工具调用。完全串行会降低效率，完全并行又可能造成写入冲突、审批绕过或历史顺序不确定。
- 创新点：工具 schema 带 `destructive` 和 `parallel_safe` 标注；同一批次内仅当所有调用均非破坏性且可并行时才并发执行；shell、文件写、memory write、request_input、未知或破坏性工具串行通过审批边界；批次结束后按模型调用顺序写回历史和 trace。
- 与现有技术区别：不是一般多工具调用，而是把安全标注、审批策略、批次并发和确定性历史回写组合成运行时规则。
- 可实施性：项目已有 `ToolSchema`、`ToolTurnContext`、`Executor`、approval provider、`fs_write` mutation metadata 等实现。

### 候选点四：提交前模型路由与失败熔断的智能体模型调用保护

- 技术背景：生产智能体常需要在主模型、备用模型或不同提供方之间切换。若在模型已经输出内容或发起工具调用后切换，容易造成重复输出或重复执行。
- 创新点：`RoutingModelClient` 对候选模型进行首个可提交事件探测；仅在尚未产生用户可见文本或工具使用提交前允许重试和 fallback；重试可尊重 rate-limit retry-after 和退避参数；认证失败、上下文长度错误不做同候选重试；共享健康状态按提供方目标打开熔断。
- 与现有技术区别：不是按请求难度选择模型，而是围绕智能体运行副作用定义“提交前可切换、提交后不可切换”的边界。
- 可实施性：项目已有 `RoutingModelClient`、`RetryPolicy`、`ModelHealthStore` 和相关测试。

### 候选点五：本地优先任务工作区的配置、状态、工具和记忆隔离

- 技术背景：智能体执行工具会读写文件、运行 shell、保存记忆。多个任务共用同一根目录时，容易发生状态污染、文件越界和记忆混淆。
- 创新点：支持 Folder、Repo、Task 三类 workspace；Task workspace 在配置或请求指定的 base 下创建单独根目录，并将 state、filesystem tool boundary、shell working directory、session memory 和 durable memory 全部重定位到任务根。
- 与现有技术区别：不是简单切换当前目录，而是以工作区为运行时边界统一约束配置解析、工具权限和记忆路径。
- 可实施性：项目已有 `Workspace::detect`、`Workspace::task`、`AppConfig::rebase_to_workspace` 和 CLI/API task workspace 路径。

## 4. 融合与选定

上述候选点可融合为一篇方法 + 系统类专利，工作标题为：

> 一种本地优先状态化智能体运行时任务恢复与工具编排方法及系统

选定理由：

- 组合闭环完整：本地工作区隔离、状态存储、上下文压缩、模型路由、工具编排和 API replay 共同服务于“智能体任务可恢复、可观测、可控执行”。
- 差异化更清晰：单个技术点容易落入日志存储、提示压缩、模型路由或工具调用的通用现有技术；组合后强调运行时副作用边界与恢复闭环。
- 可实施性强：均有项目文档和源码支撑，适合撰写方法步骤、系统模块和实施例。
- 保护范围合理：主权利要求可围绕“状态化智能体运行方法”，从属权利要求分别保护文件+索引、检查点压缩、工具批次、安全审批、模型路由、任务工作区隔离。

## 5. 建议保护主线

主保护点建议聚焦：

（1）一种本地优先状态化智能体运行方法：创建工作区和运行身份；生成文件工件与索引记录；构建含记忆和检查点的上下文；在提交前进行模型路由；按工具安全标注执行批次工具；写回有序事件和可恢复任务快照；重启或恢复时从 SQLite 与文件工件重建查询和续跑上下文。

（2）一种智能体运行时系统：包括接口层、运行引擎、上下文与检查点模块、模型路由模块、工具编排模块、状态存储模块、记忆模块、工作区隔离模块和 API replay 模块。

不建议将单一 RAG 检索、Web UI 页面、某个具体模型提供方或某个命令行参数作为主保护点；这些更适合作为实施例或从属特征。
