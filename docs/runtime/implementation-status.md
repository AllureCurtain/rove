# Current Implementation Status

This matrix compares the runtime hardening target with the current implementation.

> Web status note (2026-07-27): the C0 persistence/API foundation, C1
> continuity UI, and C2 Settings surface described below are implemented. C3
> migration/polish/live-API acceptance is not implemented.

## MVP Status

MVP reached for the local-first single-user runtime. The exact boundary, included capabilities, exclusions, golden paths, and verification baseline are documented in [mvp-definition.md](mvp-definition.md).

| Area | Current status | Remaining gap |
|---|---|---|
| Local-first default | API defaults to `127.0.0.1:8787`; CLI and state default to the workspace. Remote bind requires token auth unless explicitly marked unsafe. | None for the current local-first target. |
| Configuration | Typed config with defaults, `.rove/config.toml`, env, CLI/API overrides, validation, source summary, redacted dump output, planner prompt path, model compaction controls, shell policy fields, routing retry/backoff fields, tool/memory path settings, and named provider profiles with system-mapped wire protocols, active/fallback references, protocol options, custom headers, and bounded secret references. API and Web requests select `provider_type`; `wire_protocol` is response/diagnostic metadata, and browser requests pass only environment-variable secret names. | More CLI fields could be exposed as explicit overrides over time. |
| Repository packaging | Root `Cargo.toml` is a virtual resolver-3 Workspace with default member `apps/cli` and packages `rove-models`, `rove-core`, `rove-runtime`, `rove-app-bootstrap`, `rove-cli`, `rove-api`, `rove-bench`, and `rove-integration-tests`. A future `apps/desktop` is a new product, not unfinished migration. |
| Model package | `rove-models` owns provider-neutral messages, `ModelToolSchema`, usage, `ModelError`, `ModelClient`/`ModelEvent`, provider protocols, shared HTTP transport, the opt-in external process adapter, Fake Model, routing, and health. | Agent core package | `rove-core` owns the in-memory `Agent`, `AgentEvent`, stop outcome, cancellation/steering/follow-up control, action parser, normalized model turn, `ToolError`, `Tool`/`ToolOutput`/`ToolRegistry`, invocation-scoped `ToolContext`, operational `ToolDescriptor`, bounded argument validation, and runtime-neutral before/after policy hooks. `ToolDescriptor` projects to the narrower model schema before provider calls. | Runtime package | `rove-runtime` owns run/job/session IDs, `RunRequest`, `TaskState`, prompt checkpoints, execution-policy and plan-ledger contracts, Workspace/path enforcement, prompt metadata/runtime identity, approval/input provider contracts and task-local input registration, canonical `StreamEvent`, context/compaction, session/durable memory, local built-in tools, invocation adapters, the existing stdio/legacy-SSE MCP proxy, the tool `Executor` pipeline, pre/post-tool and post-run hooks (including session-summary), planner/step coordination, durable event translation, the persistent `Engine` facade, plus StateStore, trace/task/report artifacts, SQLite index, repair, cleanup, and resume. Cargo metadata proves its only local dependencies are `rove-models` and `rove-core`; package and root compatibility tests cover public state and memory round trips, context authority order, compaction version, event names, path and tool safety, memory promotion, request input, shell rejection, MCP registration/timeout/error/cleanup, executor metadata/hooks, session-summary hook writeback, artifact defaults, repair/resume, API restart, and custom-tool input events. | Product tool-registry assembly and first-party `AppConfig` live in `rove-app-bootstrap`. |
| Runtime core | `Engine` is public glue in `runtime/src/engine/facade.rs`; shared model turns, tool turns, unplanned loop, planned coordinator, and bounded planned `StepRunner` live in focused runtime modules. A planned step can perform multiple model/tool turns, returns every tool result to the model, and completes only on a model step conclusion. Every terminal attempt emits an append-only `StepRecord`, followed by one correlated deterministic `PlanDecision`. Initial and replacement work use immutable parent-linked `PlanRevision` values; replacement emits `plan_revised`. Stable plan/revision/attempt identity and event-derived model, tool, mutation, and token metrics are retained. Recoverable tool errors stay within the step; approval denial remains fail closed and finishes as blocked. Sugar `plan_enabled`/`max_steps` fields write into typed `ExecutionPolicy`; planned steps use an independent compatibility ceiling of four model turns. | Model-on-ambiguity evaluation, an independent Finalizer, public multidimensional execution config, global budget enforcement, and structured budget/finalization events from the future lifecycle design are not implemented. |
| State layer | Implemented in `runtime/src/state/`: files under `.rove/runs/` plus SQLite index for sessions/jobs/runs/events/reports/task states. `step_result`, `plan_decision`, and `plan_revised` in `trace.jsonl` are canonical lifecycle facts; `task_state.json` holds materialized records/decisions/revisions and any active attempt, checkpoints hold bounded lifecycle metadata, and reports include full lifecycle projections. Missing additive fields deserialize with defaults, and a legacy mutable plan is wrapped once as revision zero. WAL, foreign keys, migrations, busy timeout, lazy task-state import, TTL cleanup, and explicit `rove state repair/cleanup` commands exist. `state repair` rebuilds task-state metadata, report rows, events, and event offsets from artifacts while reporting corrupted trace lines. | Resume currently consumes the task-state projection and does not reconcile canonical trace events newer than the latest snapshot. There is no dedicated query index for lifecycle record fields. |
| API jobs | Live registry stores active handles; SQLite stores durable job/run/event state. Restart marks stale running jobs `interrupted`; historical state and SSE replay read from SQLite. Pending approval/input rows are persisted while live and marked `interrupted` on restart, but answer channels are not reconstructed by design. Explicit resume creates a new run; an unknown in-flight planned attempt becomes an `interrupted` record and error completion without replaying model/tool work. | True long-lived human-in-the-loop reconstruction and user-directed recovery from an interrupted step remain intentionally out of scope. |
| Interface runtime assembly | CLI uses a sync fast path for `dump-config` before Tokio startup. Running `rove` with no task enters a line-oriented REPL; quoted and unquoted multi-word tasks run as one-shot messages. Optional `rove tui` uses the same `CliRuntime`, `Engine`, canonical events, run artifacts, cancellation token, and approval/input providers through an alternate-screen Ratatui/Crossterm shell. Its session picker resolves persisted state through the shared `StateStore`; the timeline is an in-memory view, not a second event or persistence contract. CLI and API share the async runtime tool registry builder, including configured MCP tools. | The TUI intentionally supports one active session/run at a time. Multi-session tabs, background task management, and mouse interaction remain future product scope. |
| Full-screen TUI MVP | `rove tui` has a reducer-driven EventStream loop, bounded async run projection, a live renderer-neutral chronological timeline, wrapped transcript/history, cancellation, confirmation-before-exit, resize/narrow rendering, bounded session/tool/help overlays, hardened terminal setup/restoration, and capability-gated approval/input modals. The session picker lists only non-running persisted task states and revalidates a selected identity before resume. Non-Windows terminals with keyboard enhancement use direct `Y`/`Enter` actions. Windows uses native key events with a non-text `F8` confirmation/submission boundary because pasted text is not distinguishable from typed text. A non-clone controller opens a modal only after the canonical event and live responder match by kind and ID. Bracketed paste, held-key tracking, and a post-draw arming boundary prevent pre-modal input from resolving it. Cancellation, completion, EOF, draw failure, unsupported event capabilities, and cross-run cleanup fail closed; unsupported terminals reject approval and return a typed unavailable input error without opening a modal. Empty legacy view state uses a sanitized aggregate fallback; live updates use timeline entries. The shared driver drains post-run hooks and finalizes artifacts before publishing completion. | The standard-library real-terminal smoke is opt-in and Unix-only. Windows reports a typed skip because no native ConPTY automation is included; that skip is not a pass. Display sanitization is bounded defense in depth, not a formal guarantee for arbitrary provider text. |
| MCP compatibility | Stdio/SSE MCP clients and proxy tools live in `runtime/src/tools/mcp_proxy.rs` and register through the shared `tool_registry_with_mcp` builder. Stdio transport has request timeouts, stderr diagnostic capture, JSON-RPC error mapping, annotation-to-safety mapping, and child cleanup coverage. Package and root tests use local stdio fixtures, and an env-gated real filesystem MCP smoke test verifies the official stdio server path when enabled. | Streamable HTTP, negotiated sessions, rich result envelopes, and Tool Artifacts remain proposed; broad compatibility with secret-backed servers such as GitHub or databases remains optional smoke scope, not default CI. |
| Status semantics | `init`, `running`, `done`, `error`, `cancelled`, and `interrupted` are represented. | None for the current lifecycle target. |
| Context budgets | Implemented in `runtime/src/context/manager.rs`: token-estimated context builder with soft, hard, and reserved budgets. | Token counting is approximate, not provider tokenizer based. |
| Prompt checkpoints | `PromptCheckpoint` stores summary, preserved tail, plan, memory pointers, last step, last event seq, token estimate, compacted count, compaction metadata, and bounded step-ledger identity/count/active-attempt metadata. Full records remain in task state and trace. Optional model-generated compaction can emit richer summaries; deterministic fallback records degraded/circuit metadata and keeps resume reliable. Resume prefers checkpoint tail/summary. | Provider-tokenizer counts remain approximate under context budgets; checkpoint-to-trace ledger reconciliation remains future work. |
| Tool orchestration | Tool batches can run parallel when every call is non-destructive and `parallel_safe` and no interactive input provider is installed; interactive runtimes conservatively use the serial event/ack path because tool schemas cannot yet declare dynamic input use. Results are emitted in deterministic call order. Tool calls that depend on previous tool output naturally run in later model turns and therefore serialize. Destructive tools go through approval. Tool args get recursive schema validation for the supported subset. `write_file` reports diff/write-set metadata into `ToolResult` and reports; shell execution is timeout/output/env/denylist bounded. | No separate batch hook layer or general tool-dependency DAG inference yet. Shell write-sets are not inferred. |
| Provider abstraction | OpenAI, OpenAI Responses, Anthropic, Ollama, and Fake are peer providers behind `ModelClient`. Protocol IDs, a duplicate-safe registry, byte-safe bounded SSE/JSONL framing, redacted resolved auth/header values, shared bounded HTTP transport, and native protocol strategies are implemented. Product bootstrap uses `ProviderClient` for native HTTP primary/fallback targets; named config profiles resolve system wire protocols. API/Web request profiles select `provider_type` and expose only env-name secrets. An opt-in `external-adapter-v1` process client supports separately configured custom wire formats with bounded timeouts, env allowlisting, and secret injection. Fake remains local. | Legacy native client modules remain only as parity-test references; production cleanup and release evidence for W1 are complete. |
| Routing and fallback | Fallback models and named fallback profiles are supported through the registry-driven provider path. Fallback happens before committed visible output/tool-use, uses provider-aware target IDs, and shares API health state across jobs. Routed candidates support configured max attempts, base/max backoff, rate-limit retry-after, and no retry/fallback after committed output or tool-use. Structured tracing records probe, retry, and exhaustion outcomes. | None for the current retry/backoff target. |
| Memory layers | Storage, recall, paths, prompt loading, built-in memory tools, and the session-summary post-run hook are implemented in `runtime/src/`: working prompt memory, configured session summary files, configured durable topic files, bounded durable recall, guarded durable promotion through `save_memory`, and deterministic session summaries with goal/status/output/tool/write-set/plan-step metadata. | Durable recall is lightweight lexical relevance, not a full knowledge system. |
| Workspaces | Folder and Repo detection remain unchanged. Task workspaces can be created from CLI or API under a configured/requested base. Web/API jobs can also bind an explicit absolute Folder or Repo root, with config rebased so state, filesystem tools, shell, session memory, and durable memory are scoped to that root. C0 adds an API-global `product.sqlite` catalog for validated Folder/Repo workspaces and server-owned product sessions while execution facts stay in each workspace store. C1 makes that ProductStore catalog authoritative in the default shell. Browser/Desktop **automation workspace kinds** remain future specs. | A Tauri Desktop product host requires a dedicated D0 design/plan; automation workspace kinds remain separate future specs. |
| Built-in vector RAG | Removed from the product. Workspace retrieval is tool-based (`read_file` / `search_code` / `run_shell`) plus layered session/durable file memory. `search_code` is first-class structured search, not an embedding index. | Future optional external semantic retrieval only if separately designed. |

| API security | Config includes bind address, token auth, CORS origins, rate limit, and unsafe remote override. Middleware enforces bearer token auth, CORS allowlists, and per-process request limits. | Multi-user identity and distributed rate limiting are later deployment/product scope, not active runtime gaps. |
| Web | Standalone Next.js product shell with Workspace/Session rail, Chat, collapsible Inspector, inline tools/approvals/input/cancel, real Folder/Repo job binding, light/dark tokens, and full-page Settings navigation. The server-side `/api/*` proxy injects `ROVE_API_TOKEN` upstream while preserving SSE; `/dev/workbench` is advanced-only.
