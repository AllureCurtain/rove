## 1. 为什么这是地基

[决策 3 来自 01]: Core 是 library,接口是壳。

**地基决定**:CLI / API / Web 三个接口能不能共用同一套核心。

地基对了,后续 M5 (API)、M6 (Web) 几乎零成本。
地基错了,每加一种接口都是大改 (pico 现在的痛点)。

**Claude Code 的样板**(`claude-code-analysis/analysis/05-differentiators-and-comparison.md` § 2):

```typescript
export async function* query(
  userMessages: Message[],
  systemPrompt: SystemPrompt,
  toolUseContext: ToolUseContext,
  deps: QueryDeps,
): AsyncGenerator<StreamEvent> {
  let messages = userMessages
  while (true) {
    for await (const event of deps.claudeApi.stream(messages, systemPrompt)) {
      yield event
    }
    const toolUseBlocks = extractToolUseBlocks(messages)
    if (toolUseBlocks.length === 0) break
    for await (const update of runTools(toolUseBlocks, ...)) {
      yield update
    }
    messages = appendToolResults(messages, toolResults)
    await executePostSamplingHooks(messages, toolUseContext)
    if (shouldAutoCompact(messages)) await compactConversation(messages, ...)
  }
}
```

**这个签名同时支撑了 REPL / SDK / headless / subagent / remote 五种形态。** 这就是 rove 要达到的水平。

**Rust 等价物**:`impl Stream<Item = StreamEvent>` + `async_stream` crate。语法心智几乎一样:

```rust
pub fn ask(&self, user_message: String) -> impl Stream<Item = StreamEvent> + '_ {
    async_stream::stream! {
        // ... 主循环
        yield StreamEvent::RunStarted { /* ... */ };
        // ... 
    }
}
```

## 2. 这一份要回答的问题

### Q1: 主循环的"事件流"用什么类型?

候选:
- `impl Stream<Item = StreamEvent>` + `async_stream::stream!` 宏 ✓ **首选**
- `Pin<Box<dyn Stream<Item = StreamEvent> + Send>>` (类型擦除版本)
- 手写 `Stream` trait impl (太啰嗦)
- `tokio::sync::mpsc::Receiver<StreamEvent>` + spawn (适合解耦但麻烦)

**初步倾向**:**`impl Stream` + `async_stream`**,理由:
- 写起来像 Python `async def ... yield`,心智成本低
- 零分配 (相比 boxed)
- tokio / axum / SSE 集成天然
- Claude Code 已验证可行

类型擦除版本 (`Pin<Box<dyn Stream>>`) 在跨 crate / 接口边界需要时再用,内部 engine 不用。

### Q2: 事件流里有哪些事件类型?

用 Rust enum 表达,候选清单 (待裁剪):

```rust
#[derive(Debug, Clone, Serialize)]
#[serde(tag = "type", rename_all = "snake_case")]
pub enum StreamEvent {
    RunStarted { run_id: Ulid, job_id: Option<Ulid>, user_message: String },
    LLMStreamChunk { delta: String },
    LLMMessage { full: String, usage: Usage },
    ToolCallRequested { call_id: Ulid, name: String, args: serde_json::Value },
    ToolCallApprovalNeeded { call_id: Ulid, /* ... */ },
    ToolCallStarted { call_id: Ulid, /* ... */ },
    ToolCallProgress { call_id: Ulid, partial: String },
    ToolCallCompleted { call_id: Ulid, result: ToolResult },
    ToolCallFailed { call_id: Ulid, error: ToolError },
    PlanCreated { todos: Vec<Todo> },                // M2
    PlanStepCompleted { step_id: Ulid },             // M2
    ContextCompacted { before_tokens: u32, after_tokens: u32 },
    MemoryWritten { topic: String, summary: String },
    RunCompleted { reason: TerminationReason, output: Option<String> },
}
```

**初步倾向**:**M0 先实现核心 5 个** (RunStarted / LLMStreamChunk / ToolCallStarted / ToolCallCompleted / RunCompleted),其他按 milestone 加。

**Rust 优势**:加新变体时,所有 `match event { ... }` 编译器会强制你处理或显式 `_ => ...`。Python 的 isinstance 分发漏一个分支只能跑到 prod 才发现。

### Q3: Job vs Session vs Run,这三个抽象的关系?

**初步定义**:

| 抽象 | 生命周期 | 包含什么 |
|---|---|---|
| **Session** | 用户层概念,可以跨越多次启动 | 多个 Job 的序列 + 会话级 working memory |
| **Job** | 一次"任务",可异步、可查询、可取消 | 多个 Run (重试 / 多步) |
| **Run** | 一次主循环执行 | 多个事件、一份 trace、一份 state、一份 report |

```rust
pub struct SessionId(pub Ulid);
pub struct JobId(pub Ulid);
pub struct RunId(pub Ulid);

pub struct Session { id: SessionId, working_memory: WorkingMemory, /* ... */ }
pub struct Job     { id: JobId, session_id: SessionId, status: JobStatus, /* ... */ }
pub struct RunState { id: RunId, job_id: JobId, step: u32, status: RunStatus, /* ... */ }
```

**对照**:
- CLI 一次性命令 → 一个 Session + 一个 Job + 一个 Run
- CLI REPL → 一个 Session + 多个 Job (每次输入一个) + 每个 Job 可能多个 Run
- API → 多个 Session (用户隔离) + 异步 Job + 内部多个 Run

**待决问题**:
- Job 和 Run 真的需要分开吗?
  - **倾向分开**,因为 retry 这个事 Run 级别处理更干净
- Session 在 API 里怎么定义边界?
  - 倾向:user_id + 工作目录 + 显式 session_id

### Q4: 接口层怎么消费事件流?

**CLI 消费方式**:

```rust
use futures::StreamExt;

let mut events = engine.ask(user_message);
while let Some(event) = events.next().await {
    match event {
        StreamEvent::LLMStreamChunk { delta } => {
            print!("{}", delta);
            std::io::stdout().flush()?;
        }
        StreamEvent::ToolCallStarted { name, args, .. } => {
            println!("\n[tool] {name}({args})");
        }
        StreamEvent::RunCompleted { reason, .. } => {
            println!("\n[done] {reason:?}");
            break;
        }
        _ => {}
    }
}
```

**API 消费方式** (SSE,axum 内置):

```rust
use axum::response::sse::{Event, Sse};
use futures::stream::Stream;

async fn stream_events(
    Path(job_id): Path<Ulid>,
    State(state): State<AppState>,
) -> Sse<impl Stream<Item = Result<Event, anyhow::Error>>> {
    let events = state.engine.ask(/* ... */)
        .map(|ev| {
            Ok(Event::default()
                .event(ev.event_name())
                .data(serde_json::to_string(&ev).unwrap()))
        });
    Sse::new(events)
}
```

**Web 消费方式**:
- 后端走 SSE,前端用 EventSource API
- 前端 `new EventSource("/jobs/{id}/events")`,onmessage 里 JSON.parse

**统一点**:**接口层都是消费同一个 `impl Stream`**,差别只在"事件 → 什么显示形式"。

### Q5: 主循环的 Rust 伪代码?

**初步 (M0-M1 版,M2 加 plan 那块要扩展)**:

```rust
use async_stream::stream;
use futures::stream::Stream;

impl Engine {
    pub fn ask<'a>(
        &'a self,
        user_message: String,
        job_id: Option<JobId>,
    ) -> impl Stream<Item = StreamEvent> + 'a {
        stream! {
            let run_id = self.state_store.new_run(job_id);
            yield StreamEvent::RunStarted {
                run_id, job_id, user_message: user_message.clone(),
            };

            let mut step: u32 = 0;
            let mut history = History::new();

            while step < self.max_steps {
                step += 1;

                // 1. 构建本轮 prompt
                let prompt = match self.context_manager.build(&user_message, &history).await {
                    Ok(p) => p,
                    Err(e) => {
                        yield StreamEvent::RunCompleted {
                            reason: TerminationReason::Error,
                            output: None,
                        };
                        return;
                    }
                };

                // 2. 调模型 (流式)
                let mut full_response = String::new();
                let mut llm_stream = self.model.stream(&prompt);
                while let Some(chunk) = llm_stream.next().await {
                    match chunk {
                        Ok(c) => {
                            full_response.push_str(&c.delta);
                            yield StreamEvent::LLMStreamChunk { delta: c.delta };
                        }
                        Err(_) => break,
                    }
                }

                // 3. 解析模型输出
                let action = self.parser.parse(&full_response);

                // 4. 分流 (sum type + match,编译器保证穷尽)
                match action {
                    Action::Final(text) => {
                        yield StreamEvent::RunCompleted {
                            reason: TerminationReason::Final,
                            output: Some(text),
                        };
                        return;
                    }
                    Action::ToolCall { name, args, call_id } => {
                        yield StreamEvent::ToolCallStarted {
                            call_id, name: name.clone(), args: args.clone(),
                        };
                        match self.executor.run(&name, args, run_id).await {
                            Ok(result) => {
                                yield StreamEvent::ToolCallCompleted {
                                    call_id, result: result.clone(),
                                };
                                history.append_tool_result(result);
                            }
                            Err(e) => {
                                yield StreamEvent::ToolCallFailed {
                                    call_id, error: e.clone(),
                                };
                                history.append_tool_failure(e);
                            }
                        }
                        continue;
                    }
                    Action::Malformed { reason } => {
                        history.append_malformed_feedback(reason);
                        continue;
                    }
                }
            }

            yield StreamEvent::RunCompleted {
                reason: TerminationReason::StepLimit,
                output: None,
            };
        }
    }
}
```

**Rust 实现要点**:
- `stream!` 宏让 `yield` 写起来像 Python AsyncGenerator
- `impl Stream<Item = StreamEvent> + 'a` 把生命周期暴露出来 (借用了 self)
- `Action::Final(_) | Action::ToolCall { .. } | Action::Malformed { .. }` 三个分支编译器强制全覆盖
- 错误处理用 `match`,不像 Python try/except 会有"忘了 catch 哪一类"问题

**待决问题**:
- `stream()` 和工具调用怎么交错?Anthropic SDK 流式里直接含 tool_use block
- M2 加了 plan,主循环要不要分两层 (outer plan loop + inner exec loop)?
- retry / reflection 的计数器逻辑放哪?

## 3. 待决策的设计点

| # | 决策点 | 候选 | 当前倾向 |
|---|---|---|---|
| D1 | 主循环类型 | `impl Stream` / `Box<dyn Stream>` / channel | **`impl Stream` + `async_stream`** |
| D2 | 事件用 enum + serde 还是 JSON Value | enum + `#[serde(tag = "type")]` / dyn / Value | **enum + serde tag**,既类型安全又能直接序列化给 SSE/Web |
| D3 | Job vs Run 分还是合 | 分开 / 合并 | 分开 |
| D4 | history 怎么存 | `Vec<Message>` 在 engine 里 / 外部 store | 先 `Vec<Message>` 在 engine,context_manager 做裁剪 |
| D5 | 工具调用是 LLM 内联还是独立 step | Anthropic tool_use block 风格 / pico 的 `<tool>` 标签风格 | **Anthropic 风格** (更标准,适配 OpenAI function call 也容易) |
| D6 | parser 怎么处理 malformed | 直接 retry / 给 LLM 反馈再 retry / 放弃 | 给反馈再 retry,N 次后放弃 |
| D7 | concurrent tool calls 支持吗 | 支持并发 / 串行 | M0-M1 串行,M2+ 并发 (Claude Code 这么做) |
| D8 | id 类型 | UUID / ULID / 时间戳+nonce | **ULID** (有序、短、好读) |
| D9 | engine 是 struct 还是模块函数 | `struct Engine` + deps inject / module-level | **`struct Engine`**,deps 注入更干净 |
| D10 | 流式的取消怎么做 | drop stream / cancellation token | drop stream (Rust 天然支持 cancel-on-drop) + 内部 CancellationToken (M2+) |
| D11 | trait 用 `async-trait` 还是原生 async fn in trait | async-trait / 原生 | **`async-trait`**,直到原生稳定且支持 dyn dispatch (~2026 末) |
| D12 | prompt 在源码里还是外置文件 | `include_str!` 编译时 / 运行时加载 | **运行时加载**,避免改 prompt 重编译 |

## 4. 下一轮聊什么

按重要程度排:

1. **D5 工具调用风格** — 这决定了 prompt / parser / 模型适配层怎么写
2. **D3 + D8 Job/Run/Session 抽象** — API 阶段最依赖这个
3. **D4 history 存储** — 影响 context_manager 设计
4. **D2 + D1 事件类型与 stream 选型** — Rust 这两块比 Python 更需要落到具体 trait 签名上
5. **D6 retry 策略** — 影响主循环复杂度

也可以先聊 **Layer 5 数据类型 (types.rs) 详设计** —— 把 `Message`、`Tool`、`Action`、`ToolResult` 等所有 rove 内部传递的数据**一次性 Rust 化**,后续每个模块就有 ground truth。
