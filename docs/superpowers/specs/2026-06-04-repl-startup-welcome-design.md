# REPL Startup Welcome Design

## Goal

Improve the empty-looking REPL entry experience without adding a task-start header or a full-screen TUI. When a user starts `rove` with no one-shot message, the terminal should show a compact welcome view that gives the session a clear entry point and shows only the most useful current context.

## References

This design is based on the Claude Code analysis project at `D:\Study\project\claude-code-analysis`:

- `src/components/LogoV2/WelcomeV2.tsx` uses a fixed-width branded welcome illustration rather than a status table.
- `src/components/Onboarding.tsx` places the welcome visual above the current interactive content.
- `src/components/StatusNotices.tsx` keeps startup notices limited to information that needs attention.
- `src/components/StatusLine.tsx` and `src/components/PromptInput/PromptInputFooter.tsx` keep operational status near the prompt/footer instead of crowding the welcome view.

The key takeaway is that the startup view should create a polished entry experience. Detailed operational state belongs in `/status`.

## Scope

In scope:

- Replace the current plain REPL startup status block with a more polished welcome entry view.
- Show only stable REPL context at startup: product/version, current directory, model, session state, mode, and a short hint.
- Keep `/status` as the detailed status surface.
- Keep the implementation line-oriented and compatible with the existing `rustyline` REPL.

Out of scope:

- No task-start header.
- No full-screen TUI or alternate screen.
- No large boxed dashboard.
- No broad refactor of REPL execution, message rendering, or slash command behavior.
- No dependency-heavy terminal UI framework.

## User Experience

Startup should feel like a welcome screen, not a configuration dump. The default shape should be a fixed-width block around 50-60 columns, with a small branded title area, restrained low-contrast character decoration, and a short context area.

Example direction:

```text
  R O V E
  local agent runtime

  D:\Study\project\agent\rove

  model   qwen/qwen3-coder        session  new
  mode    repl                    status   ready

  Type your task, or use /help for commands.
```

The exact ASCII art can change during implementation, but the final output must preserve these principles:

- No surrounding dashboard border.
- No dense field list.
- Strong brand/title signal near the top.
- Directory is visible but truncated if it would dominate the layout.
- Model and session are visible as compact context, not as a table of every config value.
- The prompt appears immediately after the welcome block with normal spacing.

## Information Model

Startup welcome fields:

- `name`: `rove` or a stylized `R O V E` title.
- `subtitle`: short product phrase, currently `local agent runtime`.
- `version`: if easily available through existing CLI metadata.
- `cwd`: current directory, formatted for terminal width and truncated from the start when needed.
- `model`: active model display name or model id.
- `session`: `new` or `resumed`, optionally with a short id only if it fits cleanly.
- `mode`: `repl`.
- `status`: `ready` unless startup checks produce a meaningful warning.
- `hint`: `Type your task, or use /help for commands.`

Detailed `/status` fields remain outside the welcome view:

- provider
- full session id
- memory path
- active run/job
- approval mode
- state directory
- workspace/git details

## Rendering Behavior

The REPL startup path should continue printing once before the first prompt. The welcome block should be generated by a pure formatting function so it can be unit tested without running the REPL.

Output should remain line-oriented text written to the same stream currently used for REPL startup status. One-shot output is not part of this feature.

Terminal-width handling:

- Prefer a fixed target width of 56 columns when the terminal is wide enough.
- For narrow terminals, fall back to a simpler compact layout without decorative lines.
- Paths should be truncated from the start, preserving the most specific tail.
- Avoid layout assumptions that break on Windows paths.

Unicode handling:

- The canonical implementation should work in plain terminals.
- Decorative Unicode may be used only if the existing codebase already accepts it and tests keep a plain fallback practical.
- The design should not depend on Unicode box drawing.

Color handling:

- Color is optional and should be conservative.
- The first implementation may be monochrome.
- If color is added, it should be disabled under no-color conditions and should not make tests brittle.

## Architecture

Keep the change inside the CLI UI boundary:

- `src/interfaces/cli/ui.rs` owns the welcome formatting function and small helpers such as path truncation.
- `src/interfaces/cli/repl.rs` continues to call the formatter once before entering the `rustyline` loop.
- `/status` remains the detailed state command and should not be reduced to match the welcome view.

The formatter should accept an explicit data struct rather than reaching into global state. This keeps it testable and avoids coupling terminal rendering to runtime setup.

## Testing

Add focused tests for:

- Default wide welcome layout contains title, cwd, model, session, mode, status, and hint.
- Long Windows paths are truncated without losing the tail.
- Narrow width uses the compact fallback and does not overflow expected width.
- `/status` still exposes detailed session/status information separately.

Do not use brittle snapshots that include every decorative character unless the output is intentionally stable. Prefer assertions on structure and key lines.

## Acceptance Criteria

- Starting `rove` with no one-shot message no longer shows the current plain status table.
- The first screen has a clear branded welcome area and useful context.
- Startup output does not include task information.
- Detailed operational information remains available through `/status`.
- Existing REPL behavior, slash commands, and one-shot behavior are unchanged.
- Formatting, clippy, and tests pass.
