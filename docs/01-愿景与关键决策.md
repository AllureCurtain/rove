# rove — 愿景与关键决策

## 1. 项目愿景

> **一个自己从底层造的、本地优先、有状态、可恢复、可观测的通用 agent runtime,以 Workspace 为核心抽象,用 Rust 写。**

**它是**:一套能跑各种任务、能保存进度、能解释自己做过什么的执行平台。rove 通过不同 `Workspace` 进入不同工作世界:第一阶段是 `Folder/Repo Workspace`,后续可扩展到 `Task` / `Desktop` / `Browser`。

**它不是**:
- LangChain / LangGraph 套壳
- 特定领域 agent (医疗 / 法律 / 客服)
- 一次性问答工具
- 纯聊天机器人
- 只会写代码的 code-only agent

---

## 2. 价值目标 (为什么做)

四个回报都要,优先级排序:

1. **实现原理的掌控感** — 每一行能解释,面试讲得深
2. **拿得出手的完整产品** — 给朋友看、能跑、能演示
3. **架构 / 工程展示价值** — 状态/记忆/工具/RAG 都讲得出门道
4. **未来变现 / star 潜力** — 不强求,但架构留口子

**Rust 路径在这四个维度上都有加成**(详见决策 1)。

---

## 3. 明确的边界 (不做什么)

| 不做 | 理由 |
|---|---|
| 特定领域 agent | 保持通用性,这是项目识别度 |
| 单纯聊天界面 | agent ≠ 聊天,见 02 文档 |
| 只做代码仓库 agent | 第一阶段会先做 Folder/Repo,但 rove 的核心抽象是 Workspace,不是 Repo |
| 包装别家 agent 框架 | 失去掌控感和差异化 |
| 第一阶段做 multi-agent | 单 agent 没打磨好就上多 agent 是灾难 |
| 一上来就上 Web/Cloud | 先验证内核,接口可演化 |

## 4. 关键决策清单

### 决策 1 [锁定]:语言 = Rust

**理由**:

1. **类型系统是 agent 设计的本命场景**
   rove 的核心类型大量是 sum type:
   - `Action = Final | ToolCall | Malformed`
   - `StreamEvent = RunStarted | LLMStreamChunk | ToolCallStarted | ToolCallCompleted | ToolCallFailed | RunCompleted | ...`
   - `ToolError = UnknownTool | InvalidArgs | InvalidInput | HookBlocked | PermissionDenied | ToolExecution`
   - `RunStatus = Init | Running | Done | Error | Cancelled`
   - `TerminationReason = Final | StepLimit | TokenLimit | TimeLimit | Error | Cancelled`
   
   光高层设计就有 5+ 个 sum type,详细展开会到 15-20 个。Rust `enum` + `match` 强制穷尽性检查 —— **加新变体编译器会替你找出所有需要处理的地方**。Python 的 pydantic Discriminated Union 是运行时检查,漏一个分支要靠测试才能发现。

2. **状态机式的主循环 + 5 步工具 pipeline**
   每一步都是离散状态,Rust typestate 模式能在编译期约束转换合法性。

3. **性能 / 单二进制部署**
   长期跑的 agent daemon 内存安全 + 无 GIL + 单文件可分发。

4. **差异化 / 工程含量**
   Python agent 是主流,Rust agent 是稀缺。同样做一个 agent:
   - Python 版本:"又一个 Python agent"
   - Rust 版本:"自己包了 Anthropic 客户端 + 自己设计的状态机 + 自己接的 lancedb",**面试讲解时工程深度高 30%+**

5. **lancedb 原生 Rust**
   M3 RAG 要用的 lancedb 本来就是 Rust 写的,Rust 用反而更顺。

6. **prompt 迭代速度的反对意见站不住**
   反对 Rust 的常见点是"prompt 改了要重编译"。**实际做法:prompt 放外置 markdown/yaml 文件,运行时加载,改完就跑,不重编译。** 这条反对自动消失。

7. **MCP / Anthropic SDK 的 gap 是可控成本**
   官方 Anthropic SDK 只有 TS / Python,Rust 要自己包。但 Anthropic API 就是 HTTP + JSON + SSE,自己写一个 thin client ~200 行,**这本身就是面试可讲的工程含量**。MCP 同理。

**排除项及理由**:

| 候选 | 排除理由 |
|---|---|
| **Python** | 探索期最快,生态最完整,有 pico 心智模型。**但产出是"又一个 Python agent",差异化低。** 适合追求快速验证、想跑各种论文 idea 的场景。**作为 PyO3 绑定层,rove 未来可选** |
| **Go + eino** | eino 提供框架但我们决定不用框架;Go 没有 sum type,表达 5+ 个 enum 类型不如 Rust 干净;协程模型对长时间 agent 状态共享反而不如 Rust 类型系统 |
| **TypeScript** | 适合 Web UI 强的 agent (Claude Code 就是 TS),但后端能力一般、RAG 生态弱、类型系统不如 Rust 严 |

**关于"Rust 比 Python 慢 30-40% 出货"的预期**:
- M0 1 周 → 1.5 周
- M1 2-3 周 → 3-4 周  
- M2 2 周 → 2-3 周
- M3 1-2 周 → 1-2 周 (lancedb 原生 Rust 反而打平)
- M4 1-2 周 → 2-3 周 (MCP client 自己包)
- M5 1 周 → 1.5 周
- M6 1-2 周 → 1-2 周

**总计 3 个月 → 3.5-4 个月**。这是我们愿意付的代价。

### 决策 2 [锁定]:不用 agent 编排框架

**不用**:
- Python 世界的 LangChain / LangGraph / AutoGen / CrewAI / LlamaIndex 不会用
- Rust 世界的 `rig` / `swiftide` / `langchain-rust` / `llm-chain` 也不用

**用**:tokio、reqwest、serde、clap、axum、lancedb、candle 等基础设施 crate (详见 [03 技术栈](./03-技术栈与依赖.md))

**理由**(详细推理见 03):
- agent 是我们要建的东西本身,框架替我们做就学不到核心
- agent 抽象远未稳定 (LangChain 已大改三次),绑死会被迭代翻车
- 核心复杂度小到值得自己掌控 (主循环 ~100 行,Rust 用 async_stream 更紧凑)
- 错的抽象比缺抽象更贵 ("LangChain debt")
- 真做 production agent 的项目都不用:Claude Code、Cursor、Aider、Cline、SWE-agent、pico

**对 LangChain / LangGraph / rig / swiftide 的正确使用方式**:读源码学抽象,不作为依赖。

### 决策 3 [锁定]:Core 是 library,接口是壳

从 day 1 起:
- `rove::core` 模块不依赖任何 CLI / HTTP / UI 代码
- `rove::interfaces::cli`、`rove::interfaces::api`、`rove::interfaces::web` 都是 `core` 的薄壳消费方
- Rust 这条用 trait + `impl Stream<Item = StreamEvent>` 表达更干净

**理由**:Claude Code 已经证明 `query()` AsyncGenerator 能同时支撑 REPL / SDK / headless / subagent / remote 五种形态。**如果第一天没做对,后续每加一种接口都是大改**。

### 决策 4 [锁定]:起步 CLI,逐步演化形态

| 阶段 | 形态 | 验证什么 |
|---|---|---|
| M0-M4 | CLI / REPL | 内核、工具、记忆、RAG、MCP |
| M5 | + HTTP API (axum) | 异步 job 抽象 |
| M6 | + Web UI (Next.js 独立项目) | 端到端用户体验 |
| M7+ | + 多 agent / remote / PyO3 绑定 | 在稳固内核上扩展 |

**理由**:CLI 是反馈环最快的形态,适合内核验证。API/Web 在内核设计对的前提下成本很低。

### 决策 5 [锁定]:State / Trace / Resume 是一等公民

不是后期才加,**从 M0 就有**:
- 每次 run 有唯一 `run_id` (ULID)
- 落盘 `task_state.json` (运行中快照)
- 落盘 `trace.jsonl` (逐事件时间线)
- 落盘 `report.json` (收口聚合摘要)
- 支持中断后 resume

**理由**:这是 pico 已经做对、市面 90% agent 没做的差异化。延续并放大。

### 决策 6 [锁定]:流式 (Streaming) 默认开启

所有主循环基于 `impl Stream<Item = StreamEvent>` (用 `async_stream` crate 写起来等价于 Python 的 AsyncGenerator),不是"先做阻塞版再改流式"。

**理由**:
- 后期 Web 阶段不会推倒重写
- Claude Code 选了这条路,事件流贯穿全栈
- pico 阻塞模式是个遗憾,rove 从一开始就改掉
- Rust 流式天然适合 axum SSE + WebSocket,无需额外抽象

### 决策 7 [锁定]:核心产品抽象 = Workspace

`Workspace` 表示 agent 当前工作的世界边界。它不是 `RepoWorkspace` 的别名。

第一阶段支持:
- `Folder`:普通本地文件夹
- `Repo`:带 git 语义的文件夹增强模式

后续可扩展:
- `Task`:为一次任务创建的工作沙箱
- `Desktop`:本机桌面 / 应用窗口环境
- `Browser`:浏览器上下文

**理由**:
- 可以先做出像 Claude Code 一样实用的本地工具
- 但不会把 rove 提前锁死成 code-only agent
- "全能 agent"不作为空泛口号,而是通过 workspace adapter 逐步扩展
- 12 站请求生命周期仍然有效,但它属于 runtime 细节,受 Workspace 定位约束

详见 [07 产品定位与 Workspace](./07-产品定位与Workspace.md)。

## 5. 从 pico 继承 / 改进 / 抛弃

> 注意:pico 是 Python 项目,rove 是 Rust 项目。**继承思想,不复用代码**。

### 继承 (这些做对了,保留思想)

| pico 元素 | 为什么保留 |
|---|---|
| 工具边界 (`run_tool` 统一收口) | 安全 / 可审计的根 |
| 上下文 section + budget | 比简单截断高一个层次 |
| 分层记忆 (working / durable) | 比平铺历史智能 |
| run artifact 三件套 (task_state / trace / report) | 可复盘 / 可比较的基础 |
| 评测框架 (benchmark + FakeModelClient) | 让"变好"可被证明 |
| 文件化状态 (`.pico/` 目录) | 可手改 / 可 git / 可 diff |
| `dependencies = []` (零运行时依赖) 的极简精神 | rove 对应:Cargo.toml 严格审核,每个 crate 都要justify |

### 改进 (思想对,实现要升级)

| pico 问题 | rove 做法 |
|---|---|
| `runtime.py` 60KB 单文件 | 按职责拆 `core/{engine, executor, parser, context, planner, boundary}.rs` |
| 阻塞主循环 | `impl Stream<Item = StreamEvent>`,流式贯穿 |
| session 单一抽象 | Job + Session 双抽象 (Job 给 API 异步用) |
| 工具直接函数调用 | Tool pipeline 显式 7 步 (schema → validate → input → pre-hook → permission → exec → post-hook+diff) |
| 没有 hooks 扩展点 | 加 pre-tool / post-tool / pre-sampling / post-sampling 四类 hook |
| 没有真正语义检索 | M3 加 RAG retriever 工具 (lancedb + candle/API) |
| 没有 MCP | M4 加 MCP 客户端 |
| Action / Status 用字符串 | 全部 Rust enum,编译期穷尽性 |
| 错误用 dict + status code | `thiserror` 类型化错误 + LLM 看到的 `error_code` 枚举 |
| Python 动态类型 + 运行时校验 | Rust 编译期类型 + serde 序列化 |

### 抛弃 (走错的路或不再适用)

- urllib 手写 HTTP → reqwest + 流式 SSE
- runtime.py 塞 60KB → 拒绝大单文件 (Rust 也要遵守,800 行硬上限)
- REPL 和 one-shot 在 cli.py 耦合 → `interfaces::cli::{repl, oneshot}` 分开
- Python `Optional` + None checks → Rust `Option<T>` + 模式匹配
- `kind` 字符串字段判断动作类型 → 直接 `match action { Final {..} => ... }`

## 6. 验证标准 (Definition of Done per Milestone)

每个 milestone 完成时,必须能回答这五个问题:

1. **它能干什么** — 用户视角的一句话能力描述
2. **它的状态长什么样** — `.rove/runs/` 下生成什么、可恢复到什么程度
3. **它怎么被验证** — benchmark 或冒烟用例能跑过
4. **下一步阻塞是什么** — 明确指向下一个 milestone
5. **它是否破坏了已有能力** — 老 benchmark 不退化 (`cargo nextest` 全绿)
