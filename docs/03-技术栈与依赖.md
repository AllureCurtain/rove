# rove — 技术栈与依赖

> 这一份回答两个问题:**用哪些 Rust crate** 和 **不用哪些 crate**。

---

## 1. "框架"这个词必须先拆开

| 类型 | 干什么 | 我们的态度 | 例子 (Rust) |
|---|---|---|---|
| **基础设施 crate** | 解决一个具体、定义清晰的问题 (异步运行时、HTTP、序列化、CLI、向量) | **必用** | tokio、reqwest、serde、clap、axum、lancedb |
| **Agent 编排 crate** | 替你定义"agent 是什么、怎么跑、状态长什么样" | **不用** | rig、swiftide、langchain-rust、llm-chain |

**核心立场**:在 HTTP / 序列化 / CLI 这种**层级低于 agent** 的层面用框架,在**和 agent 同层**的编排层面自己写。

---

## 2. 为什么 agent 编排框架要单独区别对待

四个理由,每条都有具体痛点:

### 理由 1:Agent 是我们要建的东西本身
用 HTTP 框架,你不是在造 HTTP,你是用 HTTP 做产品。
用 agent 框架,**你要造的就是 agent** —— 等于让框架替你做你要学的那件事。

### 理由 2:Agent 抽象远未稳定
- HTTP 协议稳定 30 年
- serde 这种序列化抽象稳定 10 年
- tokio async runtime 稳定 ~5 年
- **rig / swiftide 都是 2024 年才有的,还在频繁改 API**

这些抽象都还是错的,只是各自错得不一样。绑死一个还在演进的抽象 = 把自己绑在还在改图纸的船上。

### 理由 3:Agent 核心复杂度小到值得自己掌控
- 操作系统 1M+ 行,自己写不来
- 数据库 50k+ 行,自己写不来
- **agent 主循环 ~150 行 Rust,工具分发 ~200 行,context 管理 ~300 行**

pico 在 Python 里证明了这个规模。Rust 因为类型系统帮忙,实际更紧凑。**能掌控的东西不应该交给框架。**

### 理由 4:错的抽象比缺抽象更贵
- serde 表达不了你的数据 → 写个 `#[serde(deserialize_with = ...)]`,一行搞定
- rig 表达不了你的 agent → 和框架斗智斗勇 OR "绕开它实现",**两套心智模型并存**

### 现实证据(production agent 都不用框架)

| 项目 | 用 agent 框架? | 用什么 |
|---|---|---|
| Claude Code | 否 | TS + Anthropic SDK + 自写主循环 |
| Cursor | 否 | TS + 自写 |
| Aider | 否 | Python + LiteLLM (只是 SDK 适配) + 自写 |
| Cline | 否 | TS + 自写 |
| SWE-agent | 否 | Python + 自写 |
| pico | 否 | Python 标准库 |
| **rove (本项目)** | **否** | **Rust + tokio + reqwest + 自写主循环** |

## 3. 推荐 stack (按 Milestone 排)

### M0-M1 核心 (~12 个 crate)

| crate | 干嘛的 | 不可替代理由 |
|---|---|---|
| `tokio` | 异步运行时 | Rust 异步事实标准,axum/reqwest 都依赖它 |
| `tokio-stream` | Stream 工具 | StreamExt、unfold 等 |
| `async-stream` | `yield` 风格的 stream 写法 | **让主循环写起来像 Python AsyncGenerator**,大幅降低 Stream 心智成本 |
| `async-trait` | trait 里 async fn | 在 Rust async fn in trait 完全稳定前必需 |
| `reqwest` | HTTP 客户端 | 流式 / SSE / JSON 全支持,事实标准 |
| `eventsource-stream` | SSE 解析 | reqwest 流式 → SSE 事件,可选,也可手写 |
| `serde` + `serde_json` | 序列化 | Rust 类型 ↔ JSON,**对应 Python pydantic 的角色** |
| `clap` | CLI 解析 | derive 风格,类型即接口,对应 Python typer |
| `tracing` + `tracing-subscriber` | 结构化日志 / trace | 比 log 现代,自带 span,trace.jsonl 就基于它 |
| `thiserror` | 类型化错误 | 库代码的标配错误模式 |
| `anyhow` | 应用层错误 | main 函数和 CLI 层用 |
| `ulid` | run_id / job_id 生成 | 有序、短、好读 |
| `dotenvy` | .env 加载 | 对应 Python python-dotenv |
| `figment` (或 `config`) | 多源配置合并 | env + file + CLI args 优先级 |
| `chrono` | 时间处理 | trace 时间戳 |

**总数**:13-14 个 crate。看起来比 Python stack 多,因为 Rust 把 "validation/CLI/serialization" 拆成多个独立 crate,而 Python 是 pydantic 一个包含全部。

### LLM 客户端

| crate | 干嘛的 | 备注 |
|---|---|---|
| `async-openai` | OpenAI / OpenAI-compatible (DeepSeek、Moonshot、本地 vLLM、right.codes) | 成熟,直接用 |
| 自写 Anthropic client | Anthropic API | **官方没出 Rust SDK**;社区有 `clust` / `anthropic-sdk-rs` 等,质量参差。**推荐自己写一个 thin client (~200-300 行)**,这本身就是工程含量 |
| 自写 Ollama client (或 `ollama-rs`) | 本地模型 | Ollama API 极简,自写更可控 |

**自写 Anthropic 不是劣势,是机会**:你能精确控制流式解析、tool_use block 处理、prompt cache 字段,而且面试讲起来比 `pip install anthropic` 强。

### M2 (Planner):加 0 个 crate

Planner 是逻辑,不需要新 crate。

### M3 (RAG):加 3-5 个 crate

| crate | 干嘛的 | 备注 |
|---|---|---|
| `lancedb` | 向量数据库 | **Rust 原生**,反而比 Python 调用顺;支持磁盘存储、版本化、混合检索 |
| `text-splitter` 或自写 | chunking | 简单 chunker 自写 100 行;复杂(代码语义分块)可用 tree-sitter |
| `tiktoken-rs` 或 `tokenizers` | token 计数 | context budget 用 |
| `candle-core` + `candle-transformers` | 本地 embedding (可选) | **HuggingFace 官方 Rust ML 框架**,支持主流 embedding 模型 |
| `hf-hub` | HF Hub 客户端 | 拉模型 |

**也可以不用 candle**,直接调 OpenAI / Voyage / Cohere 的 embedding API(走 reqwest),M3 起步推荐这条路,更快。

### M4 (MCP):自写 client (或 1 个社区 crate)

MCP 是 JSON-RPC 2.0 over stdio/SSE/HTTP,**官方没出 Rust SDK**。

| 选项 | 备注 |
|---|---|
| 自写 MCP client | ~500 行,设计自由,推荐 |
| 社区 crate (届时调研) | `rmcp` 等存在但生态早期,M4 时再 vet |

### M5 (API):加 3 个 crate

| crate | 干嘛的 |
|---|---|
| `axum` | HTTP API 框架,Rust 异步 web 事实标准 |
| `tower` + `tower-http` | 中间件 (CORS、压缩、超时、trace) |
| (SSE 内置在 axum,无需额外 crate) | 流式 |

### M6 (Web UI)

- **主路径**:独立 Next.js / SvelteKit 项目,前后端解耦,通过 rove 的 HTTP API + SSE 通信
- **可选**:`leptos` / `dioxus` 全 Rust 栈 (学习曲线陡,不推荐 M6 阶段尝试)

### 开发期工具 (非运行时依赖)

| 工具 | 干嘛的 |
|---|---|
| `cargo` | 内置,包管理 + 构建 |
| `cargo-watch` | 文件变化自动 rebuild,加速迭代循环 |
| `rustfmt` | 格式化,内置 |
| `clippy` | lint,内置 |
| `cargo-nextest` | 比 cargo test 快很多的 test runner,大项目用 |
| `cargo-insta` | snapshot 测试,适合 prompt / output 回归 |
| `cargo-machete` | 检测未使用依赖,保持 Cargo.toml 干净 |

### 测试相关 crate

| crate | 干嘛的 |
|---|---|
| `tokio::test` | 内置宏 |
| `pretty_assertions` | 更好的 assert_eq! diff |
| `insta` | snapshot 测试,prompt/output 回归神器 |
| `wiremock` | HTTP mock,测试 LLM client |
| `tempfile` | 测试用临时目录 |

## 4. 反推荐清单 (这些 crate 不用)

### Rust agent 编排框架(全部不用)

| crate | 不用理由 |
|---|---|
| **`rig`** | Rust LLM 框架,近期最活跃。但**用它就是用框架**,违背决策 2 |
| **`swiftide`** | RAG-focused 框架,把 indexing pipeline 封装了。**自己 100 行拼三个组件比它清楚** |
| **`langchain-rust`** | LangChain 的 Rust 移植,继承了 Python 那边的问题 |
| **`llm-chain`** | 较老,维护一般,同上 |
| **`kalosm`** | Floneum 的本地 LLM 框架,偏向 desktop app,不匹配 rove 定位 |
| **`genai`** | 多 provider 适配,小而干净,但**我们自己写 adapter 更可控**,pico 已证明这条路 |

**它们不是不好,是会让你学错东西**。把"agent 怎么设计"封在内部,你用着用着就不知道为什么。

### 其他可避免的

| crate | 不用理由 |
|---|---|
| 任何 `langchain-*` 移植 | 同上 |
| 重型 ORM (`diesel`/`sea-orm`) | 我们不用关系数据库,状态是文件 + lancedb |
| `actix-web` | 老牌 HTTP 框架但和 axum 重叠,axum 更现代、和 tokio/tower 集成更好 |
| `surrealdb`/`tikv-client` | 不需要分布式存储,文件够了 |

## 5. 对 rig / swiftide / langchain-rust 的正确使用方式

不是依赖,是**参考**。

- 读源码学它们的抽象 (Tool 接口 / Pipeline / Memory / Agent loop)
- 理解它们解决的问题、做的取舍
- **自己实现一遍等价但更简单、更适合 rove 的版本**

**rig 特别提一下**:它的 `Tool` trait 和 `Agent` 抽象**思路是对的**,可以参考它怎么用 Rust trait 表达 LLM/Tool/Memory 三大角色。但它的 API 演化太快,绑死成本太高 —— **学它的设计,不用它的 API**。

---

## 6. 什么时候真的可以用 agent 编排框架?

诚实承认有这几个场景合理:

| 场景 | 是否合适 | 备注 |
|---|---|---|
| 2 天黑客松赶 demo | ✅ | 速度第一,后果不用承担 |
| 目标就是用别人轮子拼,不打算理解 | ✅ | 合法选择,但和 rove 目标不匹配 |
| 公司技术栈强制 | ✅ | 政治原因,接受 |
| 某第三方集成只有某框架有 | ⚠️ | 极少数,可隔离用 |
| **rove** | ❌ | 零条沾边 |

## 7. Cargo.toml 预览 (M0-M1 版)

```toml
[package]
name = "rove"
version = "0.1.0"
edition = "2021"

[dependencies]
# Async runtime
tokio = { version = "1", features = ["full"] }
tokio-stream = "0.1"
async-stream = "0.3"
async-trait = "0.1"

# HTTP + LLM
reqwest = { version = "0.12", features = ["json", "stream"] }
eventsource-stream = "0.2"
async-openai = "0.27"     # OpenAI / 兼容 endpoint

# Serialization
serde = { version = "1", features = ["derive"] }
serde_json = "1"

# CLI
clap = { version = "4", features = ["derive"] }

# Logging
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter", "json"] }

# Errors
thiserror = "2"
anyhow = "1"

# IDs / time
ulid = "1"
chrono = { version = "0.4", features = ["serde"] }

# Config
dotenvy = "0.15"
figment = { version = "0.10", features = ["env", "toml"] }

[dev-dependencies]
tokio-test = "0.4"
pretty_assertions = "1"
insta = "1"
wiremock = "0.6"
tempfile = "3"
```

后续 milestone 加的 crate (lancedb / axum 等) 同样的 minimal 原则:每个都要 justify。

## 8. 决策汇总表

| 决策 | 选择 | 主要理由 |
|---|---|---|
| 异步运行时 | `tokio` | Rust 异步事实标准 |
| HTTP | `reqwest` | 流式 + JSON,事实标准 |
| OpenAI SDK | `async-openai` | 成熟稳定 |
| Anthropic SDK | **自写 thin client** | 官方无 Rust 版,自写可控+面试加分 |
| 序列化 | `serde` | 不可替代 |
| CLI | `clap` derive | 类型即接口 |
| 日志/trace | `tracing` | 结构化,工业标配 |
| 错误 | `thiserror` (lib) + `anyhow` (app) | Rust 错误处理双子星 |
| 向量库 | `lancedb` | Rust 原生,反而更顺 |
| Embedding | M3 起步用 API,需本地时上 `candle` | 务实路径 |
| MCP | 自写 (M4 时) | 官方无 Rust 版 |
| HTTP API | `axum` | tokio 生态最佳 |
| Web UI | 独立 Next.js (主) / `leptos` 备选 | 不强求全 Rust 栈 |
| 测试 | `cargo test` + `insta` snapshot | 标配 + 回归利器 |
| 包管理 | `cargo` | 内置 |
